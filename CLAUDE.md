# JP WOD

A Windows desktop app (Electron, vanilla HTML/CSS/JS renderer) that shows a Japanese word of the day, with example sentences generated by a local Ollama model. Missed days pile up in a backlog you can catch up on and check off. Windows 10 is the target; the Windows 11 widget board is not used.

## Product rules (decided, do not relitigate)

- One word per calendar day, chosen from a fixed shuffled rotation. A day's word never changes once assigned.
- Skipping days is fine. Every past day not checked off appears in a **Missed** backlog.
- Any day can be checked off or un-checked, from the list or from the detail view.
- The model never picks the word. Words come from `data/words.txt` (`written|reading|meaning|part of speech`, `#` comments and blank lines skipped). Ollama only writes an example sentence, an English translation, and two one-sentence notes (`grammar`, `usage`). The hiragana reading is computed in code, never by the model.
- Nothing depends on a scheduled time. The PC is often off for a day or more, so the app works out what it needs on launch, on wake from sleep, and on a timer.
- If Ollama is off or the model is missing, the app still shows the word, reading, and meaning. Sentences fill in later (see loading state below).

## Technical decisions and gotchas

- **Dates are local calendar strings** (`YYYY-MM-DD`), never UTC timestamps. Day math goes through `Date.UTC(y, m - 1, d)` so daylight saving cannot shift a day.
- **Assignment is persisted.** Store `startDate`, the shuffled `order`, and an `entries` map of date to `{ key, done, content }`. When `words.txt` grows, append new words to the end of `order` so existing days never change.
- **Seeded shuffle** (e.g. mulberry32) so tests are deterministic.
- **Irregular and exception words are registered.** `data/exceptions.txt` (`written|category|note`) records each word that behaves differently from its spelling: verbs ending in る (must be `ichidan`, `godan`, or `irregular-verb`), 来る/する, 行く (te-form), na-adjectives ending in い (綺麗, 有名), いい/よい, 大きい/小さい (大きな), and words whose list reading differs from the dictionary's (`reading-differs`). `lib/exceptions.js` holds the detection rules and `test/exceptions.test.js` fails when `words.txt` has a word that needs a line and has none (or a stale line). When adding words: run the tests, read each reported problem, check a dictionary, add the line. Never guess a verb group. This file is also the source of verb groups for the planned computed conjugation table; extend the rules in `lib/exceptions.js` (with a test) when a new kind of exception turns up.
- **Ollama host is `http://127.0.0.1:11434`, not `localhost`.** On Windows, `localhost` can resolve to IPv6 first and Ollama listens on IPv4.
- **Use `/api/chat` with `stream: false` and a JSON schema in `format`.** Validate: the fields below are non-empty strings, the sentence contains the word, the translation has no Japanese or Chinese characters, and `grammar`/`usage` contain no JSON debris (`{ } [ ]`). Match conjugated forms by dropping the trailing kana of verbs and i-adjectives (食べる matches 食べます). Retry once, then give up quietly.
- **Default model is `gemma3:12b`** (best Japanese of gemma3:4b, gemma3:12b, qwen2.5:7b, aya-expanse:8b on an 8 GB GPU; qwen2.5:7b answered in Chinese, aya wrote advanced sentences with bad readings). It is 8.2 GB so part runs on system RAM: about 13 to 25 seconds per sentence warm, longer on the first request. gemma3:4b is a fast fallback (about 1 second) with clearly worse sentences. Re-run `node scripts/try-ollama.js <model> 10 --one-review` when evaluating a model.
- **Generation timeout about 3 minutes.** The first request after launch can be slow while the model loads.
- **Generation priority:** today, then missed days (newest first, in the background after today finishes). Sentences are generated on the day, never ahead (`pendingContentDates(today, 0)`), so review words are as fresh as possible. Run on startup, on wake (wait about 5 seconds for the network), and every 10 minutes while content is missing.
- **Loading state:** while a day's sentence is generating, the detail view shows the word, reading, and meaning large with an indeterminate spinner (the request is non-streaming, so there is no real progress). It fills in without a page change. On failure it falls back to the placeholder and banner, with Regenerate available.
- **Review word:** the prompt offers exactly one word the user has **checked off** on an earlier day (never a merely assigned or missed one), picked deterministically from the date (`reviewCandidates(date)`, n defaults to 1) and marked REQUIRED in the prompt: use both the day's word and the review word. A sentence without the review word is still valid. Which review words were used is found by scanning the sentence with the same conjugation matching (`content.review`); the model's own claims are never trusted and the schema has no such field. Measured on gemma3:12b: 10 of 10 sentences used the review word with this wording, versus nonsense like "I eat water" with a soft "if it fits" instruction.
- **Notes (`grammar`, `usage`):** one English sentence each. `grammar` explains something visible in this sentence (a particle, the conjugation, an omitted subject). `usage` covers nuance, typical situations, or a common collocation, and must not mention the polite ます form. Banned topics: etymology, kanji history, pitch accent, grammatical gender or number. A third `watchOut` note (common mistakes, confusables) was tried and dropped: about 1 in 5 were correct. Grammar notes are still wrong about half the time on a 12B model; Regenerate is the safety net, and conjugation facts should move to a code-computed table.
- **Readings are computed, not generated.** `lib/reading.js` uses kuromoji (IPADIC) to turn the sentence into hiragana (`reading`, not `pronunciation`, so は stays は). The model got katakana and kanji readings wrong in about half of its tries (れすとらん written as るえすとおらん, kanji left in). The dictionary is about 17 MB; check it loads when packaged (Stage 8). `generate` requires a `reader` function.
- **Electron security:** `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, a preload exposing a small `window.api`, and a strict CSP with no inline styles or scripts. Render model output with `textContent`, never `innerHTML`.
- **IPC surface.** `lib/api.js` holds the handlers as plain functions (tested); `main.js` registers them with `ipcMain.handle` and rejects any sender that is not the main window's top frame; `preload.js` exposes `overview`, `day`, `setDone`, `regenerate`, `status`, `getSettings`, `setSettings`, and `onChanged(cb)` (returns an unsubscribe). The renderer is untrusted: every argument is validated in `lib/api.js` (dates, booleans, `host` must be http(s), `model` a short string). The main process emits a `changed` event after any data change; the renderer re-reads what it shows. `overview` items carry `hasContent` and `generating` but not the content itself; `day(date)` has the content.
- **Generation queue.** `lib/generator.js` (no Electron, tested): one day at a time, an in-flight set so a day is never generated twice (background run or Regenerate), runs coalesce, the server is checked once per run and only when something is pending. Status is the latest outcome: `ok`, `ollama-down`, `model-missing`, `error`. `ollama-down` and `model-missing` stop a run; a single-day `error` does not. Regenerate keeps the old sentence until a new one succeeds.
- **CSP lives in a `<meta>` tag, so `frame-ancestors` cannot be used there** (the browser logs an error and ignores it). Always confirm "no CSP errors" by reading the renderer console, not the terminal.
- **`JPWOD_USER_DATA`** overrides the user data folder (for tests and experiments). To check the real app, launch Electron with `--remote-debugging-port` and drive `window.api` over the DevTools protocol against a throwaway data folder.
- **Atomic saves:** write `state.json.tmp`, then rename.
- **Tray behavior:** closing the window hides it. Use `requestSingleInstanceLock`. Only register launch-at-login when `app.isPackaged`, otherwise dev runs register `electron.exe`.
- **User data lives in `%APPDATA%`**, not the install folder.

## Commands

- Run tests: `node --test test/*.test.js` (on current Node, `node --test test/` with a directory argument fails; use the glob or name the files).
- Start the app: `npm start` (once the Electron shell exists).

## Conventions

- Work in stages, one branch and one commit (or small PR) per stage, with conventional commit messages (`feat:`, `chore:`, `build:`, `ci:`, `docs:`).
- Write tests before implementation for pure logic (dates, words, store, Ollama client). Inject `fetch` into the Ollama client so tests can mock it.
- `reference/` is git-ignored and may hold a reference build for comparison only. Write real code fresh.
- Never commit `PLAN.md`; it is excluded locally via `.git/info/exclude`.
